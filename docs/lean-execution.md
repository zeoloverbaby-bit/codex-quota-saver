# Lean Execution：AI 执行治理八原则（提炼版）

> 一句话口诀：**Authority 严格，Execution 连续，Verification 成比例，Evidence 能继承就继承——普通缺陷留在任务内，只有真正跨过稳定 authority 才升级，只有真正到达人的边界才 STOP。**

本仓库解决「Codex 额度被最贵的模型干了最便宜的活」。额度浪费有两个来源：模型用错档位（由三层架构解决），以及**治理低效**——每个小缺陷都停下问人、每次小改动都全量重验、每条证据都重跑。这份文档是第二个问题的总纲：让 AI 连续干活，把额度花在真实风险上，而不是花在内部流程上。

一句话立场：**系统应该自动处理可以自动处理的事情，把真正的现实决策留给人——而不是用内部流程制造额外阻碍。**

---

## 三个根因与六类反模式（为什么要这些原则）

以下反模式提炼自方案所有者的真实项目实施（已脱敏：项目名、任务代号、治理文档编号均不出现）。

三个根因：

1. **把 uncertainty 当 conflict**——不知道私有实现怎么写，不等于 authority 不完整
2. **把 failure 当 Gate**——测试失败只是 executable feedback，不天然意味着需要人
3. **把 lifecycle event 当 Evidence invalidation**——commit、push、PR、换窗口都不天然改变产品行为

六类反模式：

| # | 反模式 | 表现 | 正确做法 |
|---|---|---|---|
| 1 | 普通缺陷也 STOP | 已授权任务内出现 RED / typing / fixture / CLI 适配问题就停下等人 | 不超执行边界、语义不变，就 `diagnose → minimal fix → focused rerun → continue` |
| 2 | 实现不确定性当治理问题 | 实现中需要新 helper / 测试辅助文件，就当成边界不匹配开变更 | 批准的创建根目录内新增私有辅助 = 普通任务工作 |
| 3 | 变更请求门槛过低 | 把 bug 修复、工具问题当变更请求候选 | 变更请求只处理 accepted authority 改变，不是修 bug 的许可 |
| 4 | Evidence 反复重跑 | 每过 commit / push / PR / 换窗口就问「要不要全量重验」 | 只看 relevant inputs 有没有变化，不看形式事件 |
| 5 | 全量验收当日常命令 | 普通修复后也跑全套验收 | 实现循环聚焦验证；全量验收是里程碑门禁 |
| 6 | 重复快照证明 | 每个远程/元数据动作前后都全量 hash + diff + 清单 | 入场做完整快照；无本地 mutation 的中间动作不重复逐文件 hash |

**边界提醒（防止矫枉过正）**：不是所有 STOP 都是过度治理——真正越过稳定 authority 边界（契约冲突、Schema 语义变更、依赖 owner 未冻结、证据身份影响可重放性）的 STOP 是合理的。该停不停，比过度治理更危险。

## 八条原则

### 1. 连续执行：授权后连续做，不因普通失败停下

任务满足开工条件、且得到明确授权后，执行方默认连续执行：

```
诊断 → 最小修复 → 聚焦复跑 → 继续
```

以下都属于任务内普通工作，不需要新的授权轮次：正常 TDD RED、拼写/导入错误、fixture、测试脚手架、可移植性问题、CLI 适配、实现缺陷、集成缺陷、私有辅助代码调整、以及已授权范围内 owner/版本不变的机械性 lockfile 更新。

**普通 RED ≠ 阻塞，普通 bug ≠ 变更请求。**

### 2. STOP 必须稀缺：只在人的 authority 边界停

真正需要 STOP 的情况只有：已接受的对外契约要改变、写入边界必须扩大、Schema/迁移语义改变、依赖 owner/版本/库权威改变、安全/隐私/事实/数据丢失边界要削弱、稳定跨任务接口或证据 owner 改变、真正的 authority 冲突、当前授权内无法恢复的环境阻塞、以及到达 verified 需要人验收。

不要为了「可能有风险」提前 STOP——在风险真的跨过 authority 边界时才 STOP。

### 3. 失败先分类：四类 taxonomy，分类描述观测、不自动决定治理

只使用四类失败标签：

| 分类 | 含义 | 典型例子 |
|---|---|---|
| `owned_expected_red` | 本任务预期内的失败 | 正常 TDD RED、未完成实现 |
| `preexisting_regression` | 既有回归 | 旧测试在本改动前已挂 |
| `toolchain_or_environment_gap` | 工具链/环境缺口 | 环境权限、引号转义、行尾处理 |
| `authority_conflict` | 稳定语义缺失或互相冲突 | 契约矛盾、越权诉求 |

分类是**描述观测**，不是治理结论——分完类再判断它属于普通修复、任务级调整还是变更请求。

### 4. 三层判定：普通修复 / 任务级调整 / 变更请求

| 层级 | 触发条件 | 动作 |
|---|---|---|
| 普通修复 | 在已授权范围内、稳定语义不变 | 直接修，不产生额外治理 |
| 任务级调整 | 只需调整单个任务的执行边界（失效路径、新增私有辅助路径、共享注册点、测试路径），稳定契约/Schema/安全/owner 不变 | 走任务调整，不开变更请求 |
| 变更请求 | 改变已接受的 authority：稳定契约、Schema 语义、生命周期、依赖权威、安全/隐私边界、证据 owner、跨任务稳定接口 | 必须走变更请求 |

**变更请求是 authority 变更机制，不是 bug 修复许可。**

### 5. 开工条件要「够开工」：不在开工前消灭所有不确定性

开工条件只回答一个问题：**在当前授权下能否安全开工**——不要求在实现前消灭全部私有实现不确定性（那应由 TDD 在实现中收敛）。不要因为「未来可能出现某 helper」「某 SDK 可能不好用」就提前开变更请求或无限扩张开工条件。滚动规划：只对下一批 1–2 个候选任务完整冻结开工条件，不机械预审整个未来 backlog。

### 6. Evidence 继承：输入没变就不重跑

证据是否需要重跑，取决于 **relevant inputs 有没有变化**——而不是「换了 SHA / 窗口 / PR 状态」。可以继承的典型情形：已接受的 authority/依赖未变、相关源码树未变、测试/工作流/清单/lockfile/迁移未变、执行方 owner/接口未变、树相等已证明、纯文档改动未改变运行时输入。

因此：commit / push / Draft PR / 状态流转 / 纯治理变更，都不自动要求全量重跑。但有一条铁律：**合并后主分支的干净证据必须绑定真实 merged SHA**——候选证据可以继承，主分支证据必须由实际合并后的自然工作流建立。

### 7. 验证成比例：验证深度与改动深度成比例

不要所有动作都跑同一套「大验收」：

| 改动类型 | 验证深度 |
|---|---|
| 产品/运行时改动 | 聚焦测试 → 受影响的集成/回归 → 安全/隐私/静态检查（按影响面） |
| 测试/工作流改动 | 只跑受影响的门禁 |
| 文档/纯治理改动 | 引用一致性、稳定 ID/路径一致性、diff 完整性 |
| 纯元数据改动 | 只核身份与前后状态（head SHA 不变、文件集合不变） |
| 打包产物 | 字节未变则继承实现证据 |

**全量验收是里程碑门禁，不是实现循环里的日常命令。**

### 8. 生命周期与交付门禁：不得「顺手连跳」

连续执行不省略人的授权。生命周期必须保持：

```
blocked → ready → authorized → in_progress → verified → accepted
```

并且各环节不自动等于下一环节：ready ≠ authorized；verified ≠ accepted；accepted ≠ 已提交/推送/PR/合并；合并就绪 ≠ 合并授权；已合并 ≠ 干净主分支。

人可以一次性组合多个非合并动作（验收记账 + commit + push + Draft PR），只要每步 guard 没漂移，动作之间不必反复 STOP。但 **merge 永远要求独立、明确的授权**；合并后也不能直接宣称干净主分支，必须绑定真实 merged SHA、parents、树相等与门禁成功记录。

## 决策流程（速查）

```
当前真正缺的是什么？
        │
        ├─ authority 缺失？────────── YES → 找人授权 / 任务级调整 / 变更请求
        │
        └─ NO
              │
              ├─ 在已授权范围内？────── YES → 诊断 → 最小修复 → 聚焦复跑 → 继续
              │
              └─ NO → 任务级调整 / 变更请求（按三层判定）
              │
              ├─ 相关证据已失效？────── NO → 继承
              │
              └─ YES → 按比例复验
              │
              ├─ 达到 verified？─────── YES → STOP，等人验收
              │
              └─ NO → 继续
```

## 与本仓库的映射：八原则在三层架构里的落地

| 原则 | 本仓库组件 | 落地方式 |
|---|---|---|
| 1 连续执行 | `global/agents/luna-worker.toml` | 「有界执行包」：包内普通缺陷连续修，不停不回头 |
| 2 STOP 稀缺 | `global/AGENTS.md` + luna-worker 的 STOP 条件 | 只有边界条件与「到达 verified」才 STOP |
| 3 失败分类 | `docs/pitfalls.md` | 15 个实测坑 = 观测原料，可按四分类归因 |
| 4 三层判定 | `next-step.md` 交接协议 + 网页 GPT 规划层 | 普通修复 = 主线程/执行包内直接修；任务级调整 = 回规划层改写下一步；变更请求 = STOP 报告人 |
| 5 够开工 | `project/dot-codex/next-step.md`（覆盖式交接） | 交接只写「唯一下一步」，不预审整个未来计划 |
| 6 Evidence 继承 | `eval/` A/B 评测协议 | 证据按任务/turn 归因，只重跑输入有变化的证据 |
| 7 验证成比例 | 教程验收清单、`bridge/README.md` 冒烟三连 | 部署验收分层：改什么验什么，桥改动只冒烟不全量重验 |
| 8 不连跳 | 三层架构「人 = 授权层」 | 网页 GPT 只能写下一步、Codex 只执行、验收与方向决策在人 |

## 出处与边界（诚实条款）

- 本原则提炼自方案所有者在真实 AI 协作项目中固化的执行治理规则（AGENTS 级），公开版做了**脱敏与通用化改写**：项目名、任务名、人物与私有流程细节均不出现
- 四分类与三层判定的命名做了通用化处理，与源项目的治理文档并不逐字对应
- 原则 1/2/8 已在本仓库的 `global/AGENTS.md` 与 luna-worker 定义中落地为可执行规则；原则 4 落地为交接协议约定；原则 3/5/6/7 落地为流程文档——尚未形式化为机器可执行的检查，如实标注
